# Contexte de reprise — KaraFun Plus

État relevé le 29 septembre 2026 pour reprendre le projet avec un autre agent, sur un autre PC. Dépôt public : https://github.com/jpfroud/karafun-plus. Ce document ne contient ni code de télécommande, ni clé ou jeton d'accès, ni lien QR personnel, ni données de participants. Il distingue les tests hors ligne des comportements constatés sur la vraie installation KaraFun.

## Mission et état livré

KaraFun Plus est une application web locale pour gérer la file d'un bar karaoké. Les clients scannent le QR de leur table pour choisir des titres, les gérants pilotent la soirée, et le serveur communique avec la télécommande de KaraFun pour envoyer les chansons. Cette communication utilise un protocole observé, **non garanti comme API publique**. La priorité du produit est une rotation équitable, notamment après les duos, sans faire repasser quelqu'un avant les chanteurs encore jamais montés sur scène lorsqu'un autre ordre est possible.

Le dépôt GitHub public a une branche `main` et une release Windows historique **v0.1.0**. Les sources **v0.2.0** (retours de l'essai au bar du 29 septembre : rotation, Battle, bonus/malus, connexion KaraFun) sont décrites plus bas ; elles ne sont dans aucun ZIP tant qu'une release n'a pas été publiée. Son ZIP contient `KaraFun Plus.exe`, Node.js, Java 21, Timefold, les dépendances et le guide ; KaraFun lui-même s'installe séparément. La CI et le workflow de release ont été verts sur v0.1.0. Les corrections décrites ci-dessous correspondent aux sources **v0.1.1** préparées sur `fix/solo-battle-v0.1.1`. Après clonage sur un autre PC, vérifier `git status`, `git log` et les releases pour identifier la version effectivement publiée et télécharger son ZIP.

**Une release est un instantané :** les corrections réalisées après v0.1.0 ne figurent dans un ZIP GitHub qu'après commit, CI verte et nouvelle release. Ne pas écraser le tag v0.1.0 pour représenter un code différent.

## Architecture utile

- `server.js` : API HTTP, page du bar, port client séparé, synchronisation et envoi KaraFun, orchestration de la soirée.
- `scheduler.js` : personnes, tables, listes de titres, duos, rotation, priorité, réservation du prochain passage et prévisions.
- `solver/` : worker Java Timefold (`QueueScore.java` reprend la même politique que `scheduler.js#_pick`) et pont Node dans `solver/bridge.js`. L'ordre local est calculé **immédiatement** ; Timefold part de cet ordre et cherche mieux en arrière-plan (budget **3, 8 ou 15 secondes** selon la taille, **30 secondes** pour le bouton « Recalculer la file »), après une seconde de regroupement. Son ordre n'est adopté que s'il est **strictement meilleur** selon la mesure locale `_planMetric` (reprises de table, retours trop rapprochés), ou si le score Timefold progresse au niveau dur ou moyen (part des tables, premiers passages) sans dégrader cette mesure et que la règle locale reproduit exactement cet ordre ; sinon il « confirme » l'ordre affiché, qui ne bouge pas. **Optimisation continue** (`continuousSolver`, active avec le vrai solveur) : tant que l'empreinte de la file ne change pas, des passes de 10, 20 puis 30 s repartent du plan adopté avec une autre graine (`randomSeed`), avec les mêmes règles d'adoption ; après trois passes sans gain, la pause entre passes double jusqu'à 2 min. Une vraie modification interrompt la passe ; l'ordre manuel du bar n'est jamais remplacé. Sur le scénario de l'essai au bar, les passes suivantes réduisent encore nettement les reprises de table (voir `RAPPORT-TEST.md`). L'interface du bar ne nomme pas Timefold (« Ordre optimisé », « Optimisation continue »). Un plan survit au passage normal des chansons (réservation, envoi, fin) et n'est remplacé qu'après un changement réel. Le processus Java reste actif toute la soirée : une nouvelle requête interrompt la précédente (`terminateEarly`) au lieu de redémarrer la JVM. Un résultat périmé est ignoré.
- `battle-vote.js` : vote Battle, sélection du titre, pause entre votes et suivi de l'automatisation.
- `karafun.js`, `kcs-transport.js`, `karafun-state.js` : communication et interprétation de l'état KaraFun ; `fake-karafun.js` fournit un simulateur hors ligne.
- `table-access.js` : QR et accès des tables ; `solo-invitations.js` : invitations personnelles « En solo » à usage unique ; `song-repeats.js` : détection des titres en double (déjà prévus ou chantés récemment) ; `night-state.js` : sauvegarde de la soirée et reprise après crash ; `catalog.js` : recherche dans le catalogue KaraFun.
- `public/staff.html`, `public/client.html`, `public/print.html`, `public/app.css` : pages bar, clients et QR.
- `start-evening.js`, `launcher/`, `KaraFun Plus.exe` dans le kit, `DEMARRER.bat` et `ARRETER.bat` : démarrage et arrêt Windows.
- `test/` : tests unitaires, simulations de soirée, API avec faux KaraFun, tests du kit. `RAPPORT-TEST.md` est le rapport local, avec les résultats les plus récents **en tête** ; des sections historiques plus anciennes peuvent décrire des limites déjà corrigées.

Le port **3000** sert au bar et doit rester privé. Le port **3001** sert aux clients, écoute sur `127.0.0.1` et est le seul point à exposer par un tunnel HTTPS. Les deux ports et leurs droits sont distincts. Les fichiers `data/` conservent la soirée et ne sont pas publiés dans le dépôt ou le kit de release. `journal/` contient des journaux locaux et n'est pas publié non plus. Ne pas copier ces dossiers dans une question publique ou un ticket sans examen préalable.

## Règles fonctionnelles à préserver

Chaque chanteur peut préparer plusieurs chansons et en changer l'ordre tant qu'elles ne sont pas déjà dans KaraFun. Un téléphone peut gérer plusieurs personnes de sa table, mais ne peut modifier que les personnes qu'il a inscrites ou récupérées. Un transfert par QR code ou lien (paramètre `reprise`, secret de 128 bits, 30 min, usage unique, envoyable par WhatsApp/SMS/e-mail) ou, en secours, par code court à 4 chiffres (10 min, 5 essais) transfère la gestion vers le nouveau téléphone et révoque l'ancien accès pour cette personne ; le premier moyen utilisé annule l'autre. L'ouverture du lien n'affiche qu'une confirmation (« Récupérer … ») : un aperçu de lien ne consomme rien. Le bar obtient le même QR si le téléphone précédent est perdu ou déchargé. Quand un titre choisi est déjà prévu dans la file ou a été lancé dans KaraFun depuis moins de `repeatWarnMin` minutes (45 par défaut, 0 coupe ce volet), la page prévient sans bloquer, avant et après l'ajout ; la file du bar porte un repère de doublon (`song-repeats.js`, historique `playedSongs` sauvegardé avec la soirée).

La rotation place les chansons déjà chargées dans KaraFun avant les passages encore calculés. Timefold impose l'ordre des titres de chaque chanteur et pénalise fortement le deuxième passage physique d'une personne lorsqu'un chanteur prêt n'est jamais passé. Le **participant invité à un duo garde son propre titre et son tour**, mais sa présence sur scène compte dans l'équité et espace son retour. Le chanteur qui lance le duo consomme le passage de sa chanson. Un duo au sein de la même table est direct ; un duo entre tables ou avec une personne « En solo » demande l'accord de l'invité. Le bar peut noter après coup un duo improvisé avec n'importe quelle personne de la salle. Les personnes de la même table doivent être proposées d'abord dans la sélection.

Politique de rotation (v0.2.0, complétée le 30 septembre), dans l'ordre : premiers passages de la soirée avant tout retour ; une fois par tour (crédit de tour ajusté par bonus/malus) ; au plus **deux passages sur scène par personne et par tour** (`roundAppearanceCap`, compteur `roundApps` sauvegardé et annulé avec un passage non chanté), les duos au-delà attendant le tour suivant et les personnes privées de passage par ce plafond passant en tête du tour suivant (liste `roundOwed`, sauvegardée, gardée jusqu'au passage de chacune, même avec un invité déjà monté dans le tour) ; un duo noté par le bar après l'envoi rejoint le reçu du titre (annulé avec lui) et libère le prochain annoncé qu'il ferait dépasser le plafond ; au moins **trois autres chansons** entre deux passages d'une même personne (`spacingSongs`) quand un autre passage du tour le permet sans reprise de table, un premier passage pouvant ainsi attendre trois chansons au plus ; pas deux fois de suite la même table quand une autre peut chanter ; partage du tour entre tables selon le mode ; espacement d'une personne qui vient de chanter. Trois modes, mêmes champs d'API (`tableRotation`, `weightedTables`) : « Chacun son tour » (défaut, part au prorata des chanteurs prêts), « Tables à tour de rôle » (parts égales), « Compromis » (racine du nombre de chanteurs). Le partage utilise l'écart entre la part méritée et les passages obtenus sur une fenêtre glissante d'environ un tour (`recentGroups`). Option `interleaveArrivals` (active par défaut) : quand tous les passages prioritaires viennent de la table qui vient de chanter, une personne d'une autre table peut s'intercaler si elle n'a chanté avant aucune personne encore en attente depuis son dernier passage (`readySerial`) ; ainsi une grande table arrivée tard ne monopolise pas le micro et personne ne chante deux fois pendant l'attente d'un nouveau. Changer de mode ne remet plus à zéro le tour des personnes. Les chanteurs du groupe « En solo » comptent comme des groupes de rotation distincts. Bonus/malus (-3 à +3) par table ou par personne : réservé au bar, jamais exposé aux clients ni au journal public ; il change la fréquence (crédit de tour 1/poids) et la part de la table, jamais la priorité des premiers passages. Une place **annoncée comme la prochaine après la scène** est réservée ; un nouvel arrivant ou un recalcul ne doit pas la lui retirer. Un départ, un titre retiré ou une action explicite du bar peuvent encore changer cette place. Les autres rangs et heures restent des prévisions, qui peuvent bouger après changement d'état et à la publication du nouveau résultat Timefold. L'interface distingue « Dans KaraFun », « Titre suivant » et les autres titres « À venir » ; la place et l'heure des titres futurs sont indicatives.

Le bar peut avancer un titre avec « Priorité », déplacer des passages par glisser-déposer et annuler ses interventions manuelles une par une ou toutes. Depuis v0.2.0, **seule la ligne déplacée bouge** : l'ordre affiché des autres est figé (plan « manuel ») jusqu'au prochain changement réel ou au bouton « Recalculer la file », et Timefold n'est pas relancé. L'annulation rétablit l'ordre et le plan d'avant l'intervention si la file réelle n'a pas changé. Le bar peut aussi retirer plusieurs titres d'un coup (`/api/staff/remove-many`, y compris un titre suivant précis d'une liste) et consulter les derniers passages sur scène (`stageHistory`, sauvegardé avec la soirée). Une priorité ne déplace pas les titres déjà dans KaraFun. « Vider toutes les chansons » garde les tables, les chanteurs et leur historique ; « Supprimer toutes les tables » lance une nouvelle soirée et invalide les anciens QR. Les retraits dans KaraFun doivent être confirmés par sa file réelle avant de reprendre les envois. Les gérants peuvent marquer une personne partie puis la réactiver en conservant son historique. L'option « Je suis là » ne demande confirmation qu'à la personne qui passe **juste après** celle sur scène ; pour un duo, la réponse de l'un des deux suffit (`confirmedForTurn`). Depuis v0.3.0 elle **ne bloque plus** : sans réponse `presenceGraceSec` secondes (30 par défaut) après que la scène s'est libérée, `skipUnconfirmed` laisse passer le passage suivant et marque la personne `presenceRetry` ; la prévision (`_forecast`), `select()` et `_commit` la replacent juste après ce passage, comme prochaine annoncée. Au bout de `presenceMaxSkips` manques (3), le titre est retiré et `maybeGone` alerte le bar (« Toujours là » / « Marquer parti »). Le groupe « En solo » n'a plus de nombre de places. En mode « Compromis », la part d'une table se calcule sur ses personnes qui ont encore un titre : une personne partie ne compte plus, quel que soit l'effectif déclaré. Les alertes du bar se ferment une à une ; l'avis de changement de nom KaraFun (après environ 2 minutes de refus du nom habituel) est aussi effacé côté serveur. La version affichée au bar vient de `build-info.json` (écrit par `PREPARER-KIT-BAR.ps1`, version de la publication et commit), sinon de `package.json` et du commit git local.

La Battle se propose depuis la page client avec **un à trois titres**. Chaque personne déjà inscrite au lancement du vote dispose d'une voix, même sans chanson ; elle choisit un titre ou « Pas de Battle ». Depuis v0.2.0, le vote dure un temps réglable (**5 minutes** par défaut, compte à rebours visible) et se décide **avec les votants** : il faut au moins **5 votants** (réglable ; en dessous de ce nombre d'inscrits, la salle ne peut pas proposer de Battle et le bouton est masqué) et plus de voix pour la Battle que pour « Pas de Battle ». Les résultats par titre sont affichés en direct ; le titre le plus voté gagne, à égalité le premier proposé. Le vote se clôt dès que tout le monde a voté, et le bar peut le clore. La pause entre Battles (**15 minutes** par défaut) part de la **fin de la Battle** (ou de la clôture d'un vote échoué). Le bar peut aussi lancer une Battle sans vote sur un titre du catalogue (`/api/staff/battle/launch`), sans délai pour lui mais avec la pause après. Le bouton Lecture du bar lance une Battle prête en tête de KaraFun (`remote.PlayRequest`), y compris une Battle créée dans KaraFun. Le bar reçoit une alerte. Le logiciel tente l'ajout en mode Battle seulement si la télécommande l'autorise ; sur la vraie installation testée, **KaraFun a refusé la permission Battle**. L'application annonce immédiatement le refus et passe à l'organisation manuelle dans KaraFun. Ne pas relancer aveuglément l'ajout après une incertitude d'accusé de réception. Le bar laisse rejoindre les participants et démarre la Battle lui-même. La lecture automatique ne doit ni démarrer la Battle, ni lancer aussitôt le titre suivant après les résultats. Une Battle ajoutée directement dans KaraFun doit également entraîner cette pause. Le QR natif Battle de KaraFun peut donner accès à la télécommande : **tester les permissions KaraFun Pro depuis un téléphone invité avant de le montrer au public** ; le compte de l'application doit garder ses droits d'administration.

## Correctifs de la v0.1.1 et limites vérifiées

1. **Accès « En solo ».** La faille de v0.1.0 venait du QR commun partageable : avec un autre téléphone ou une navigation privée, on pouvait créer d'autres profils. Depuis v0.1.1, le bar remet à chaque personne seule une **invitation personnelle par QR, à usage unique, valable 30 minutes**. Le QR commun ne permet plus l'inscription. Une invitation consommée ou révoquée ne peut plus servir ; une panne d'écriture lors de l'inscription restaure sa validité. Un téléphone solo ne voit et ne gère que son propre chanteur. Le transfert par code reste possible si le téléphone est perdu ou déchargé. Ces chemins sont couverts par les tests hors ligne ; la correction n'est pas dans la release v0.1.0.
2. **Battle réelle.** L'essai sur KaraFun a fait apparaître un refus de permission pour l'ajout automatique en mode Battle. Le code local détecte ce refus, l'affiche au bar et garde la demande pour une Battle créée manuellement. Les tests avec le faux KaraFun couvrent le cas où l'ajout est autorisé et confirmé, ainsi que le refus, les accusés tardifs, les Battles natives et la pause après résultats. Ils ne prouvent pas qu'une installation KaraFun quelconque donnera les permissions nécessaires. Tester les droits du QR natif avant usage public reste indispensable.
3. **Libellés et notifications.** Le texte « Passage prévu » a été remplacé par une distinction plus courte entre titre dans KaraFun, titre suivant et titres à venir. Les pages clients et bar proposent « Activer les notifications ». Les demandes de duo, les votes Battle et la confirmation de présence produisent une alerte dans la page ; son/vibration dépendent de la page ouverte, et une notification système quand la page est masquée exige un contexte HTTPS et l'autorisation du navigateur. Les tests de composants et un contrôle local en navigateur couvrent l'affichage et la demande d'autorisation ; la réception sur un téléphone physique n'est pas encore validée.

**Retours de l'essai au bar du 29 septembre (v0.2.0).** Mesures reproductibles (`test/bar-rotation-feedback.test.js`, 25 soirées « table de 10, de 4, de 5, un solo, une chanson chacun et quelques duos ») : l'ancien ordonnanceur local donnait exactement le même ordre en mode personnes et en rotation des tables (165 reprises de table sur 594 passages, séries de 9 ; 100 reprises dans le seul tour des 20 solos). La différence ressentie au bar venait de Timefold, qui en mode personnes n'avait **aucune** contrainte de table, et du fait que l'ordre local décidait presque toujours du prochain (fenêtre de 2,5 s, plan invalidé à chaque fin de chanson). Le mode « grandes tables » était neutralisé par un tour strict des tables appliqué avant la pondération, et changer de mode effaçait le tour en cours. Après correction, en « Chacun son tour » : 74 reprises sur 594 (essentiellement des duos entre tables en fin de liste), 9 dans le tour des solos, série max 2 dans ce tour ; aucun « deuxième passage avant un premier » dans les trois modes. Le nom `FileKaraoke-XXXX` changeait à chaque reconnexion KCS : les droits d'administrateur donnés dans KaraFun étaient donc perdus. Il est désormais stable (`data/karafun-login.json`), redemandé pendant ~30 s si KaraFun garde l'ancienne connexion, et l'envoi automatique coupé faute de droits reprend seul à leur retour. **À vérifier sur la vraie installation** : que KaraFun rattache bien les droits au nom (et non à la seule connexion), et que `remote.PlayRequest` démarre une Battle en tête de file.

**Timefold et la stabilité de la file :** la recherche approfondie dure 3, 8 ou 15 secondes selon la charge (30 s sur demande du bar). La soirée n'attend jamais le solveur pour fixer le prochain chanteur. La file future n'est mise à jour que si Timefold trouve un ordre meilleur (règle ci-dessus) ; les passes continues sans gain ne la font pas bouger. Le prochain déjà réservé reste à sa place, sauf indisponibilité ou intervention explicite du bar. Les changements rapides sont regroupés et les calculs périmés sont ignorés.

## Développement, tests et livraison

Lire `AGENTS.md` et `.codex/README.md` avant les changements. Le projet impose un parcours gstack adapté (`gstack-investigate` pour un bug, `gstack-qa` pour le navigateur, `gstack-review` avant livraison) ; si une compétence ne fonctionne pas, consigner l'échec et la vérification équivalente sans prétendre l'avoir exécutée. Le hook Claude Code vérifie gstack ; le hook Codex de `.codex/hooks.json` doit être examiné puis approuvé après clonage. Pour les tables, duos, présences ou la file : ajouter des régressions ciblées, lancer `node test/run-offline.js`, vérifier l'interface touchée et compléter `RAPPORT-TEST.md`.

Depuis les sources, installer avec `npm ci`, construire le solveur avec Java 21 et Maven (`mvn -B -ntp -f solver/pom.xml verify`), puis lancer `node test/run-offline.js`. Le test de l'intégration Timefold se trouve dans `test/timefold-integration.test.js` ; des simulations de six tables représentatives et de 60 clients sont dans la suite. `npm run demo` et `fake-karafun.js` servent aux essais qui modifient la file. **Ne pas utiliser la session KaraFun réelle pour les tests destructifs.** La CI Windows se lance sur `main` et les PR, reconstruit Timefold, lance les tests hors ligne, teste le hook et le kit portable. Le workflow « Release Windows » se lance sur un tag `v*` ou manuellement depuis `main`, refait les tests, construit le ZIP et publie son SHA-256 avec la release.

Le serveur Socket.IO utilisé par le faux KaraFun est passé à **2.5.1** pour corriger [GHSA-25hc-qcg6-38wj](https://github.com/advisories/GHSA-25hc-qcg6-38wj). Le client Socket.IO 2.x reste nécessaire à la compatibilité avec la télécommande historique de KaraFun ; une migration vers 4.x exige des essais de protocole, pas une mise à jour automatique des dépendances. L'audit npm du 29 septembre signale encore des alertes faibles ou modérées héritées de cette famille, sans alerte élevée ou critique. Ne pas confondre absence d'alerte élevée et preuve de sécurité de l'exposition Internet.

**Vérifications observées sur les sources v0.1.1 le 29 septembre :** `node test/run-offline.js` s'est terminé par « T1 et recette approfondie hors ligne OK » (journal synthétique `journal/recette-2026-09-29-v0.1.1-final.log`). L'intégration Timefold ciblée a passé **18 tests sur 18**, dont un vrai solveur sur **60 chanteurs et 90 titres** avec budget de 15 secondes ; les tests couvrent notamment la file vide, les ajouts rapprochés, la réservation du prochain et les réponses périmées. Le benchmark reproductible `test/timefold-budget-benchmark.js` compare 1,5, 10, 15 et 30 secondes sur 90 titres : les contraintes principales progressent nettement de 1,5 à 10–15 secondes, tandis que 30 secondes n'apportent qu'un léger gain secondaire ; d'où le plafond de production à 15 secondes. Les tests hors ligne valident invitations solo, refus Battle, duo, présence, restauration après crash et isolation des accès. Un contrôle local en navigateur à largeur de téléphone a vérifié les QR solo et la demande d'autorisation des notifications ; il ne remplace pas un essai sur téléphones physiques ni une recette KaraFun réelle complète. Consulter la section la plus récente de `RAPPORT-TEST.md`, en tête du fichier, avant une nouvelle publication.

**Pour reprendre ou publier :** partir de la dernière branche et du dernier tag effectivement disponibles sur GitHub, relancer les tests, vérifier le kit Windows et la CI, puis télécharger **le ZIP de la release visée** pour le tester sur le PC cible. Ne pas remplacer silencieusement un ancien tag par un code différent.

## Exploitation au bar et limites externes

Sur le PC Windows sans outils de développement, télécharger la dernière release, décompresser le ZIP entièrement, puis ouvrir `KaraFun Plus.exe` dans `karaoke-bar`. Il tente de démarrer KaraFun et ouvre la page du bar ; si KaraFun n'est pas trouvé, l'ouvrir manuellement. Activer la Télécommande de KaraFun, saisir son code actuel dans la page du bar et vérifier l'état « connecté ». Si le code change, le ressaisir ; l'application ne peut pas le découvrir automatiquement. `DEMARRER.bat` aide à lire les erreurs de lancement. Arrêter via « Arrêter la soirée » ou `ARRETER.bat`, puis sauvegarder **tout** `data/` après arrêt. Le bouton d'arrêt de l'application ne ferme pas KaraFun et ne vide pas sa file native.

Pour un essai local, les téléphones sont sur le même Wi-Fi que le PC. Pour la 4G/5G, il manque encore un **domaine HTTPS stable et un tunnel nommé** vers `http://127.0.0.1:3001` uniquement. Ne publier ni le port 3000 ni son lien de gestion. Employer ensuite le domaine HTTPS pour tous les QR clients, y compris sur le Wi-Fi ; sinon leurs accès passent en HTTP. Tester les parcours sur téléphone physique et les droits KaraFun Pro avant d'imprimer les QR définitifs. La procédure détaillée et les limites sont dans `GUIDE-BAR.md`. Pour les personnes seules, le bar génère une invitation individuelle depuis son interface : ne pas afficher un QR commun comme autorisation d'inscription. Les notifications système dépendent de HTTPS et de l'autorisation du téléphone ; le système actuel n'est pas une notification push qui fonctionnerait après fermeture de la page.

Ne jamais copier dans un échange public `data/`, un journal brut, une clé de gérant, un code KaraFun ou un lien QR personnel. Sur un autre PC, vérifier le tag et la version du ZIP téléchargé : la release v0.1.0 ne contient pas les corrections décrites ici.
