# KaraFun Plus

File de karaoké pour un bar : les clients choisissent leurs titres depuis le QR de leur table et les gérants pilotent la rotation et la file KaraFun. L'application est une interface web, servie par un PC Windows (kit) ou par un serveur Linux (image Docker), qui communique avec la télécommande KaraFun. Ce protocole n'est pas une API publique garantie par KaraFun.

## Démarrage

**Kit Windows.** Sur le PC du bar, télécharger et décompresser le kit Windows de la dernière release, puis double-cliquer sur **KaraFun Plus.exe**. KaraFun doit être installé séparément ; activer sa télécommande et saisir son code sur la page du bar. Le kit contient Node.js, l'optimiseur de file et son Java intégré : aucun outil de développement n'est nécessaire sur ce PC. Voir [le guide du bar](GUIDE-BAR.md) pour les QR, les droits, la sauvegarde et l'accès des téléphones hors Wi-Fi.

**Serveur Linux.** L'image Docker `ghcr.io/jpfroud/karafun-plus` fait tourner la file sur un VPS, derrière Caddy en HTTPS (Let's Encrypt) ; KaraFun reste sur le PC du bar. Installation, bascule depuis le kit, accès des gérants, sauvegardes et mises à jour : [DEPLOIEMENT-SERVEUR.md](DEPLOIEMENT-SERVEUR.md).

Pour accueillir une personne venue seule, le bar émet un QR individuel depuis sa page de gestion. Il crée une seule place dès son ouverture, puis reste la clé de la soirée : rouvert sur un autre téléphone, il propose de récupérer les mêmes chansons. Il n'y a pas de QR commun « En solo » à afficher, sauf en mode « Événement privé » (bar privatisé), où un seul QR inscrit chaque nouveau navigateur qui le scanne (un autre téléphone, ou une autre application sur le même téléphone). Pour un changement de téléphone, le téléphone actuel (ou le bar) affiche aussi un QR code de transfert, envoyable en lien par WhatsApp, SMS ou e-mail, avec un code à 4 chiffres en secours.

Pour travailler depuis les sources : `npm ci`, Java 25 et Maven pour construire `solver/pom.xml`, puis `node test/run-offline.js` pour la recette isolée. `npm run demo` démarre une simulation sans toucher à KaraFun. Le workflow « Tests » construit le solveur et lance les tests sous Windows et sous Linux, puis vérifie le kit et l'image Docker. Un tag `v*` lance le workflow « Release », qui publie le kit et l'image `ghcr.io/jpfroud/karafun-plus` ; il peut aussi être déclenché manuellement depuis GitHub, mais seulement depuis `main`.

**Version de test d'une branche** (sans publication) : chaque exécution de « Tests » garde le kit construit pendant 14 jours. Ouvrir l'onglet Actions → « Tests » → « Run workflow », choisir la branche, puis, une fois l'exécution verte, télécharger l'artefact `kit-bar-test-…` en bas de sa page. Il contient `KIT-BAR-KARAFUN.zip`, à décompresser sur le PC du bar comme une release. Une PR produit le même artefact automatiquement.

Les fichiers `data/`, `journal/`, `deploy/.env`, les archives de `deploy/sauvegardes/` et les codes de télécommande ne doivent pas être publiés. Les QR clients donnent accès à une table ; le lien de gestion du bar reste privé.

**Sécurité et mises à jour des dépendances.** Une faille se signale en privé (voir [SECURITY.md](SECURITY.md)). Dependabot propose chaque semaine les nouvelles versions des dépendances npm et Maven, des actions GitHub et des images Docker, et les correctifs de sécurité dès leur publication ; les correctifs mineurs fusionnent seuls une fois la CI verte, jamais l'optimiseur (Timefold et ses autres dépendances Maven : bilan avant/après du workflow « Bilan Timefold »), Socket.IO et sa pile (protocole KaraFun) ni les actions GitHub (droits de la publication). Les workflows « CodeQL » et « Sécurité » (revue des dépendances, `npm audit`, Trivy sur le dépôt, l'image et l'image publiée, zizmor sur les workflows) tournent sur chaque PR et chaque semaine, « OpenSSF Scorecard » chaque semaine et sur `main`. Chaque release porte des SBOM CycloneDX et des attestations de provenance. Sur un serveur Linux, la carte « Mise à jour » de la page du bar permet aussi de revenir à une version précédente en cas de problème ([DEPLOIEMENT-SERVEUR.md](DEPLOIEMENT-SERVEUR.md), section 17).

Pour proposer un changement : [CONTRIBUTING.md](CONTRIBUTING.md). Un [document de reprise](CONTEXTE-REPRISE.md) résume l'architecture, les décisions et les limites pour poursuivre le projet avec un autre agent.
